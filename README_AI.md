# AI 语音热敏打印机（env: ai_voice）

在原有打印测试工程（`ble_iprint` / `serial_printer`，已实测硬件可用）基础上，
新增的 **语音 AI 对话 + 热敏打印** 固件环境。**不影响原有两个环境。**

> 老陈实测确认（2026-10-02）：屏幕 **ST7789**（与 lib/TFTDisplay 一致）、
> 打印头 **JX-2R-17**（384 点、6 组×64 点分时加热，与 ThermalPrinter 库一致）。
> 假设全部落定，无需改硬件配置。
>
> **2026-10-03 改版**：屏幕改 **横屏 320×240**；中部显示「你说 / AI 回答」；
> 改成 **免按键对话**（VAD 常时监听，按键只作唤醒/打断）。详见第 8 节。

## 编译烧录

```bash
pio run -e ai_voice -t upload && pio device monitor
```

## 硬件依据

引脚 = 《Netlist_PCB1_18 网表》交叉核对《立创实战派S3》实测库（lib/ 下的
ThermalPrinter / TFTDisplay 注释即本板接线），两处完全吻合：

| 功能 | 引脚 |
|---|---|
| 打印 DI/CLK/LAT/STB | 6 / 7 / 43 / 5 |
| 打印头 Vdd / VH | 47(低=开) / 48(高=开) |
| 纸电机 IN1~IN4 | 15 / 16 / 17 / 18 |
| 温度 ADC / 缺纸 | 4 / 3（⚠️ 实战派 IO3 已知硬件损伤，缺纸检测不可用）|
| 屏 MOSI/SCK/CS/DC/BL | 40 / 41 / 11 / 39 / 42 |
| I2C SDA/SCL | **1 / 2**（⚠️ 旧测试代码 ble_print.cpp 写的 41/42 与网表不符，本环境已改正）|
| I2S MCK/BCK/WS/DOUT/DIN | 38 / 14 / 13 / 45 / 12 |
| 功放使能 PA_EN | 46 |
| 电池 ADC / 充电检测 | 9 / 10 |
| 按键（唤醒/打断） | 8 |
| 外设总电源 | 44（高=开，最先初始化）|

## 使用流程

1. 上电 → 开机动画 → WiFi 配网（首次长按无反应时手机连热点 `AI-Printer-Setup`）
2. **直接说话就行，不用按键** —— 检测到你开口自动开始录，说完约 0.7 秒静音自动结束
3. 语音命令：
   - 「打印」/「打出来」→ 打印上一条 AI 回复
   - 「音量大一点 / 小一点 / 音量百分之60 / 最大音量 / 静音」→ 调音量（NVS 断电记忆）
   - 「电量」→ 语音播报电量
   - 其他任何话 → 走大模型对话 → 语音播报 → 说「打印」可打出回复
4. 屏幕（横屏 320×240）：
   - 顶部状态栏：WiFi 信号格 + dBm、电池电量 + 充电闪电，每 5 秒刷新
   - 中部：「你说」绿色 + 「AI 回答」白色（太长会截断，右下角三个点表示还有内容）
   - 底部状态行：听你说… / 识别中… / 思考中… / 说话中…
5. 空闲 60 秒自动关背光，说话或按按键唤醒（不是真休眠，只是关屏省电）

## 上线前必改

`src/ai/ai_config.h`：

- `BAIDU_API_KEY` / `BAIDU_SECRET_KEY`：百度智能云「语音识别」+「语音合成」应用
- `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`：任意 OpenAI 兼容接口（默认 DeepSeek）

TTS 用百度 `aue=5`（PCM 16k）直出，**无需 MP3 解码库**，省资源。

## 实话实说（未验证项）

- 本环境代码**未在实机上运行**（打印/屏幕库除外——它们是原工程实测过的）。
- ES8311/ES7210 的寄存器序列用的是 lib/ 里的库 + 通用初始化，若录音没声/播放没声，
  优先查：① I2C 地址扫描确认 0x18/0x40；② MCLK 是否 1.024MHz~（16k×64）；
  ③ I2S 声道格式（ONLY_LEFT/RIGHT 可能要换）。
- 语音命令里的"百分之60"数字解析按 UTF-8 字节偏移取的，ASR 若回
  "百分之六十"汉字数字则不识别，后续可加汉字数字转换。
- 大模型/百度接口的 JSON 字段按当前公开文档写的，平台改版需跟进。

## 重启 / 死机排查（重要）

固件已内置诊断，**烧录后先开串口监视器看日志**，别猜。

### 1. 看复位原因

开机第一行会打印：

```
[BOOT] 复位原因 = 9 (★电压跌落(供电不足!))
```

| 打印值 | 含义 | 怎么办 |
|---|---|---|
| **9 ★电压跌落** | 电池供电撑不住瞬时电流 | 换满电电池 / 插 USB 试；固件已把 WiFi 发射功率降到 11dBm + 开 modem sleep，仍掉电就是电池内阻大或 3V3 LDO 余量不足 |
| **4 ★程序崩溃** | 代码异常（会跟一串 backtrace）| 把 backtrace 发我，或按下面"分模块排查"定位 |
| **5/6/7 ★看门狗** | 某处卡死太久 | 看 `[STAGE]` 停在哪一行 |
| **3 软件复位** | 正常（ESP.restart() 触发）| — |

### 2. 看 STAGE 停在哪

启动过程每步都打印，**最后一行就是它死的地方**：

```
[STAGE] boot                   heap=... psram=...
[STAGE] power_ctrl on
[STAGE] printer begin
[STAGE] tft + bootAnim
[STAGE] wire begin
[STAGE] audio begin
[STAGE] wifi done
[STAGE] button ready
[STAGE] status bar
[MAIN] ai_voice ready —— 若这行之后重启，看上一行 STAGE
```

### 3. 看心跳

正常运行时每 5 秒一行：

```
[BEAT] 15s heap=... psram=... wifi=3 rssi=-58
```

**心跳停了 = 重启**，配合 STAGE 就能算出是几秒后死的。

### 4. 分模块排查（决定法）

`src/ai/ai_config.h` 里改开关，一个个关掉再烧：

```c
#define AI_ENABLE_WIFI   1   // 0 = 跳过联网（测裸机，先排除 WiFi 功耗问题）
#define AI_ENABLE_AUDIO  1   // 0 = 跳过 ES8311/ES7210 + I2S
#define AI_ENABLE_UI     1   // 0 = 跳过屏幕
#define AI_ENABLE_PRINT  1   // 0 = 不初始化打印头
```

最省事的第一次测试：**四个全改 0**，只留串口。能稳定跑心跳 → 逐个开回来，
开到哪个开始重启，元凶就找到了。

### 5. 已知的两个内存炸弹（本次已修）

- ASR 原来走 base64：6 秒录音 192KB → base64 256KB+，内部 RAM 只有 320KB，**一点就崩**。
  现已改为**原始 PCM 直传**（百度支持 raw body，`Content-Type: audio/pcm`）。
- TTS 返回的 JSON 里带 base64 音频，几十秒能到 1MB+。原来 `getString()` 整个读进内部 RAM，
  现已改为**流式读进 PSRAM + 手工取字段**。
- 录音上限从 10s 降到 **6s**（够说指令，省 PSRAM）。

### 6. 2026-10-03 实测定位：状态栏"充电闪电"导致除零崩溃（已修）

**现象**：WiFi 连上后、刚显示开机圆环就重启，无限循环。

**日志关键行**：

```
[STAGE] button ready           heap=265004 psram=8217335
Guru Meditation Error: Core  1 panic'ed (IntegerDivideByZero).
PC      : 0x42019d52
Backtrace: 0x42019d4f 0x42006f81 0x4200720c 0x42007d72 0x4201dc56
```

**定位方法**（以后遇到崩溃照做，一条命令出结果）：

```bash
"C:/Users/Administrator/.platformio/packages/toolchain-xtensa-esp32s3/bin/xtensa-esp32s3-elf-addr2line.exe" \
  -pfiaC -e ".pio/build/ai_voice/firmware.elf" \
  0x42019d4f 0x42006f81 0x4200720c 0x42007d72 0x4201dc56
```

输出：

```
TFTDisplay::fillTriangle(...)  at lib/TFTDisplay/TFTDisplay.cpp:514   ← 崩溃点
StatusUI::drawBattery(...)     at src/ai/status_ui.cpp:29            ← 画闪电
StatusUI::drawBar()            at src/ai/status_ui.cpp:58
setup()                        at src/ai_print.cpp:195
```

**根因**：`TFTDisplay::fillTriangle` 用 `dy01/dy02/dy12` 作除数，而闪电三角的下边两点
`(x+9,y+7)`、`(x+14,y+7)` **同一 y** → `dy12 = 0` → 整数除零。
只要插着 USB（`CHG_DET > 1.2V` → 判为充电中）就必崩；纯电池供电反而不崩。

**修复**：重写 `fillTriangle` 为逐行扫描版，所有除法前判零，退化成水平线时走 `fillRect`。
`lib/TFTDisplay/TFTDisplay.cpp`（`F:\AI_Print` 与 `F:\print260619` 已同步）。

> 教训：第三方绘图库里凡是"用两个点的坐标差做除数"的函数，画到特殊形状（水平边 /
> 竖直边 / 退化三角形）都可能除零。状态栏、开机动画这类实时绘制的代码最容易踩。

### 7. 语音识别（ASR）失败排查 —— 2026-10-03

**现象**：`[UI] Recognizing...` 之后 `[UI] ASR FAIL`，但串口一条 `[ASR]` 详情都没有。

**原因**：上一版的 `fetchBaiduToken()` 三条失败路径**全都没有日志**，静默返回 false，
所以看不出是 Key 没填、网络失败、还是百度拒绝。

**现在**：开机自检 + 全路径日志。上电后串口会直接告诉你答案，屏幕也会显示
`Voice OK` / `Voice KEY ERR`：

| 串口打印 | 含义 | 对策 |
|---|---|---|
| `[NET] ★★ 百度 Key 还没填！` | `ai_config.h` 里还是占位符 | 去 ai.baidu.com 控制台建**语音技术**应用，把 API Key / Secret Key 填进 `src/ai/ai_config.h` |
| `[NET] token HTTP xxx: ...` | 网络或 HTTPS 失败 | 看冒号后返回内容；确认设备能上网 |
| `[NET] token 被拒: invalid_client — ...` | Key 错误 / 应用类型不对 | 必须是"语音技术"类应用（不是文字识别等） |
| `[NET] token JSON 解析失败` | 返回内容异常 | 把打印内容发我 |
| `[ASR] err 3301` | 音频质量太差 | 靠近麦克风、环境安静；检查 ES7210 增益 |
| `[ASR] err 3302` | 鉴权失败 | token 过期，重启设备 |
| `[ASR] err 3304` | 配额用完 | 控制台看剩余额度 |
| `[ASR] err 3300` | 输入参数不正确 | 把日志发我 |
| `[ASR] HTTP xxx` | ASR 请求网络失败 | 网络问题，重试 |
| `[ASR] PSRAM 不足` | 内存分配失败 | 极少见，重启设备 |

**本次改动（三处）**：

1. `ensureToken()`：三条失败路径全部打日志；Key 还是占位符时直接点名报警。
2. `asr()`：改回百度**官方 JSON 方式**（兼容性最好）。base64 与整个 JSON body
   都在 **PSRAM** 里拼装 —— 之前担心的"256KB 撑爆内部 RAM"在 PSRAM 上不存在
   （板上有 8MB），所以两种顾虑都不占。
3. `dev_pid` 从 **15372 → 1537**。15372 是"极速版"专用参数，
   标准版接口 `vop.baidu.com/server_api` 不认。

> 排错顺序建议：**先看开机那一行 token 结果**。token 拿不到 → 100% 是 Key 的事，
> 跟麦克风、音频格式无关，别去调 I2S。

## 8. 2026-10-03 改版：横屏 + 对话显示 + 免按键

实测已经跑到 ASR 成功（`[ASR] "设置一下，现在说话行吗？"`），说明录音链路完全正常。
本次按需求做了三件事。

### 8.1 屏幕改横屏（320×240）

- `lib/TFTDisplay` 新增 `setRotation()`，宽高改成运行时变量（原来写死竖屏）。
- `src/ai_print.cpp` 在 `tft.begin()` 后调用 `tft.setRotation(SCREEN_ROTATION)`。
- 开机动画、状态栏已按横屏重新排版。

**画面不对怎么调**：`src/ai/ai_config.h` 里的 `SCREEN_ROTATION`：

| 值 | MADCTL | 效果 |
|---|---|---|
| 0 | 0x00 | 竖屏 240×320（原样）|
| **1** | **0x60** | **横屏 320×240（默认）** |
| 2 | 0xC0 | 横屏，画面左右/上下翻转 |
| 3 | 0xA0 | 横屏，另一个镜像方向 |

> 三个横屏值只是镜像/翻转方向不同。开机后文字上下颠倒或左右镜像，就换 2 或 3。
> 串口会打印 `[TFT] rotation=1 320x240 MADCTL=0x60` 方便确认。

### 8.2 屏幕上显示说的话和 AI 回复

新增 `src/ai/screen_text.cpp`：

- 复用 `text_bmp.cpp` 里那份 U8g2 全 GB2312 中文画布（`cnCanvas`）——**不另开一份实例**，
  省 7.7KB RAM 和一份字库。
- 渲染流程：U8g2 画中文 → 1bpp 纵向瓦片 → 逐行转 RGB565 → `pushPixels()` 打到屏上。
- 版面（横屏 320×240）：

```
┌────────────────────────────────┐ y=0
│ WiFi 3格 -25dB      电池 82% ⚡│  ← 状态栏 26px（StatusUI）
├────────────────────────────────┤
│ 你说                            │  ← 青色
│ 设置一下，现在说话行吗？         │  ← 绿色（你说的话）
│ ────────────────────────────── │
│ AI 回答                         │  ← 黄色
│ 好的，现在可以说话了……          │  ← 白色（AI 回复）
├────────────────────────────────┤
│ 听你说… / 思考中… / 说话中…     │  ← 橙色状态行
└────────────────────────────────┘ y=240
```

- 字用 wqy16（全 GB2312），每行约 19 个汉字；「你说」区 2 行、「AI 回答」区 4 行，
  超出会截断并在右下角点三个小点提示。
- AI 回复太长想看全文 → 说「打印」，热敏纸上是完整版。

### 8.3 免按键对话（VAD 常时监听）

原来必须按住 GPIO8 说话；现在改成**常时监听**，按键只当唤醒/打断：

- `src/ai/audio_io.cpp` 新增 `listenBegin() / listenPoll() / listenResume()`：
  - 麦克风按约 32ms 一帧切片，算 RMS 能量。
  - 环境噪声底自适应（慢速滑动平均，只在"明显不是语音"的帧上更新）。
  - 能量连续 3 帧超过 `噪声底 × VAD_MULT` → 判定开口，开始录。
  - 连续 22 帧（约 0.7 秒）低于阈值 → 判定说完，进入识别。
  - **300ms 预滚环形缓冲**：判定开口时把之前 300ms 也倒进录音，避免"第一个字被吃掉"。
  - 超 6 秒强制结束。
- 播报期间不监听；播报结束 `listenResume()` 清掉 DMA 里扬声器的余音并冷却 250ms，
  防止自己的声音把 VAD 触发（自激）。
- 按键 GPIO8：任意时刻按一下 = 唤醒屏幕 + 丢掉半截录音重新听 + 一声提示音。

**灵敏度调不好就改这几个**（`src/ai/ai_config.h`）：

| 宏 | 默认 | 说明 |
|---|---|---|
| `VAD_MULT` | 3.0f | 阈值 = 噪声底 × 该值。**容易误触发就调大**（4~5），**要它灵敏点就调小**（2~2.5）|
| `VAD_MIN_RMS` | 450 | 阈值下限，防安静环境里一点风声就触发 |
| `VAD_ON_FRAMES` | 3 | 要连续几帧超阈值才算开口（调大更稳重，但反应变慢）|
| `VAD_OFF_FRAMES` | 22 | 静音几帧算说完（约 0.7s）。**它老打断你说话就调大**（35≈1.1s）|
| `VAD_PREROLL_MS` | 300 | 预滚长度。**开头字被吃掉就调大** |
| `VAD_ENABLE` | 1 | 改成 0 即退回"按住按键说话"的老模式 |

> ⚠️ 串口会打印判定过程：`[VAD] 开始说话 rms=1234 thr=560 noise=187`。调参就靠它——
> 如果明明没说话却频繁出现"开始说话"，看 noise 和 rms 的差距，把 `VAD_MULT` 调大。

### 8.4 空闲关背光

60 秒无交互自动关背光（`IDLE_SCREEN_OFF_MS`）。**注意：这不是真休眠**，WiFi 和麦克风
仍在工作，只是关屏省电。要做到真正的"睡眠唤醒"需要进 deep sleep + WiFi 重连，
牵扯较多，需要的话再说。

```c
#define LLM_BASE_URL  "https://api.xxx.com"     // 只填到域名，不带 /v1
```

## 10.3 ★ 花屏根因（已修）

`src/ai/screen_text.cpp` 原来把 U8g2 缓冲当成「8×8 块状布局」读：

```cpp
// ❌ 错的（旧代码）
row[(x >> 3) * 8 + (x & 7)]      // 位置算错 + byte 序也错
```

U8g2 的 `u8g2_ll_hvline_vertical_top_lsb` 实际是**纵向字节布局**：

```c
offset = (y & ~7) * tile_width;      // tile_width = 384/8 = 48 → 8 行带 = 384 字节
ptr    = buf + offset + x;           // x 每 +1 → ptr +1
bit    = y & 7                       // LSB = 该 8 行带最上面那一行
```

即 **`buf[(y>>3)*384 + x]` 的第 `(y&7)` 位**。校验：最大下标
`(159>>3)*384 + 383 = 7679`，正好等于缓冲大小 7680−1 ✓。

同时发现 `TFTDisplay::pushPixels()` **没做字节序转换** —— ST7789 16bpp 要求高字节
先发，而 `uint16_t` 数组在 ESP32 内存里是小端。两处叠加 = 下半屏一片彩色噪声。
两处都已修，**打印那条路（`tileToPrintLines`）是同一个错，也一起修了**。

## 10.4 ★ VAD「说话没反应」根因（已修）

1. **算 RMS 没去直流偏置**：ES7210 输出有 DC 偏置时，"安静"帧的 RMS 也有几百，
   自适应噪声底被顶得很高 → 阈值永远够不着。现在逐帧减去均值再算 RMS。
2. **噪声底只上不下**：现在开机先标定 250ms 环境噪声底，之后「低于本底快速跟随、
   高于本底极慢上升（时间常数约 30 秒）」，不会被说话声抬走。
3. **`VAD_MIN_RMS` 450 太高**（−37dBFS），小音量说话触发不了 → 降到 **200**，
   倍数 3.0 → **2.2**。

## 11.1 ★ 文字乱码的根因：U8g2 缓冲布局读反了

上一版我按"纵向字节"（像 SSD1306 那样 `buf[(y/8)*W + x]`，bit = `y&7`）
去读 U8g2 的缓冲区。**这个假设是错的。**

翻 U8g2 自己的源码：

```
src/clib/u8g2_d_setup.c
    u8g2_Setup_st7586s_jlx384160_f()
        u8g2_SetupBuffer(..., u8g2_ll_hvline_horizontal_right_lsb, ...)
                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

src/clib/u8g2_ll_hvline.c  (行 245 / 350)
    offset = y * tile_width(48) + (x >> 3);
    mask   = 0x80 >> (x & 7);
```

结论：**ST7586S 是 `horizontal_right_lsb`**，也就是

| 属性 | 真实情况 |
|---|---|
| 取法 | `pixel(x,y) = buf[y*48 + (x>>3)] >> (7-(x&7)) & 1` |
| 排列 | **行优先**，一行 48 字节 |
| 位序 | 每字节 8 个**水平**像素，**MSB 在最左** |

所以 `tileToPrintLines()` 从"逐个 bit 转置"简化成**按行 memcpy** 就行。

## 11.2 ★ 喇叭没声音的根因：TTS 返回的根本不是 JSON

百度短文本在线合成有两条完全不同的路：

| 请求方式 | 返回内容 |
|---|---|
| `GET ...?tex=原文(urlencode)` | **直接是二进制音频流** |
| `POST json`，或 `tex` 传 **base64** 文本 | JSON（`{"err_no":0,...,"speech":"<base64>"}`） |

我们的代码走的是**第一种**，却按**第二种**去 `strstr(body, "\"err_no\":")`
——二进制音频流里当然没有这个字符串，于是 `err` 恒等于 `-1`，
整段音频被当成错误丢掉，`playPcm()` 一次都没被调用过。

日志里那句 `[TTS] err -1` 就是这么来的：**它不是"百度返回了 -1 错误"，
是我们自己默认值没找到 JSON 就报 -1。**

现在改成：

```cpp
if (body[0] == '{') {   // 只有首字节是 { 才是错误 JSON
    ... 打印 err_no / err_msg ...
    return nullptr;
}
// 否则整段就是 PCM，直接拿去播
```

另外两处：
- `aue` 从 5 改成 **4**。`5` 是 pcm-**8k**，按 16k 播会变成快放怪声；
  `4` 才是 pcm-16k，和 I2S 采样率对齐。
- 万一带了 `RIFF` 头，就地前移 44 字节剥掉。

改动文件：`src/ai/cloud_ai.cpp` 的 `tts()`。

## 11.4 音量映射错误（喇叭即使有声也是蚊子叫）

`ES8311` 的 DAC 音量寄存器 `0x32`：`0x00 = -95.5dB`，`0xBF = 0dB`，
`0xFF = +32dB`，**每步 0.5dB**。

原来直接把"用户音量 150"当寄存器值写进去 → `(150-191)*0.5 ≈ -20.5dB`，
比 `init()` 里设的 `0xDF(+16dB)` **低了 36dB**。所以就算 TTS 数据通了，
也是几乎听不见。

现在做映射：用户档位 `0~255` → 寄存器 `0xC0(+0.5dB) ~ 0xFF(+32dB)`，
任何档位都在"听得见"的区间里，静音交给 MUTE 寄存器。

- 默认音量 `REC_VOL_DEFAULT: 150 → 190`（约 +24dB）
- NVS 键名 `vol → vol2`，强制作废旧值
- `beep()` 振幅 `8000 → 16000`

**另外加了个开机自检音**（`setup()` 里 `audio.begin()` 之后立刻 beep 一声）。
这一声不走网络：

- **听得到 "嘀"** → 喇叭 / 功放 / I2S / ES8311 通路全通，后面没声就是云那头的事
- **听不到** → 先查 `PIN_PA_EN`(GPIO46) 极性和喇叭插头，别去怀疑百度

## 12.1 ★ 麦克风「听不见」的真根因：ES7210 从来没配过 I2S 数据格式

`lib/ES7210/src/ES7210.cpp` 的 `init()` 里配了 PGA、MICBIAS、ADC、上电时序、
HPF —— **唯独没有碰 `0x11 (SDP_CFG1)`**，也就是"每个样本多少位"这个寄存器。
芯片复位后它默认是 `0x00`，含义是 **24bit**。

而我们的 ESP32 I2S 是按 `I2S_BITS_PER_SAMPLE_16BIT` 收的 —— 每 3 字节的样本
被当成 2 字节解析，字节整个错位，样本几乎恒定不变。

现象完全对得上：

```
[VAD] peak=1 noise=8 thr=200 br=1024     ← 去直流 RMS 恒为 1，样本基本不动
[ASR] "我不知道。"                        ← ASR 收到一堆静音，只能瞎猜
```

而且**按键强制录音走的是同一条 I2S 读取路径**，所以一样没用 —— 这正好解释了
老陈那句"原来按按键时好像能听到我说的"：能听到的那会儿，代码里还有
`es7210.setFormat(0, 16)`；我在改版 3 收拾 `setMICBias(true)` 的时候，
顺手把它也删了。

修复（`src/ai/audio_io.cpp`）：

```cpp
es7210.init();
es7210.setFormat(0, 16);   // ← 这一行绝对不能删！I2S 格式 + 16bit
```

另外加了一段**开机寄存器回读**，I2C 到底有没有真的配上，一眼就能看出来：

```
[AUDIO] ES7210 fmt=0x4C bias=0x70 pga=0x10 adc1=0x02
                ↑ 必须是 0x4x 才是 16bit
```

| 读数 | 判断 |
|---|---|
| 全是 `0xFF` | I2C 根本没应答 → 查地址/接线/供电 |
| `fmt` 不含 `0x40` | 不是 16bit，数据必然错位（就是我们踩的坑） |
| `bias` 高位为 0 | MICBIAS 没打开，麦克风不会有信号 |

## 13.1 ★ 真凶：ES7210 的字长寄存器，库写错了值

查了两份权威资料，结论一致：

- **Waveshare 版 ES7210 数据手册**，REGISTER 0x11 – SDP INTERFACE CONFIG 1：
  ```
  bit[7:5] SP_WL:  000=24bit  001=20bit  010=18bit  011=16bit  100=32bit
  bit[4]   SP_LRP     bit[3:2] Reserved     bit[1:0] SP_PROTOCOL(00=I2S)
  ```
- **Espressif 官方 `esp-bsp/components/es7210/es7210.c`**：
  ```c
  case ES7210_I2S_BITS_16B: reg_val = 0x60; break;
  case ES7210_I2S_BITS_18B: reg_val = 0x40; break;   // ← 关键的一行
  case ES7210_I2S_BITS_24B: reg_val = 0x00; break;
  case ES7210_I2S_BITS_32B: reg_val = 0x80; break;
  ```

再看我们 `lib/ES7210/src/ES7210.cpp`：

```cpp
void ES7210::setFormat(uint8_t format, uint8_t bits) {
    uint8_t val = format;
    if (bits == 16) val |= 0x40;      // ★ 0x40 是 18bit！16bit 应该是 0x60
    else if (bits == 24) val |= 0x00;
    else if (bits == 32) val |= 0x80;
    writeReg(ES7210_SDP_CFG1, val);
}
```

所以 `setFormat(0, 16)` 实际把芯片设成了 **18bit**：
ESP32 按 16bit 槽位读 18bit 的流 → 依然整体错位 →
`[VAD] raw=5`、`peak=1`、ASR 只能回"我不知道"。

**修法：绕过库，直接写寄存器。**

```cpp
es7210.init();

i2cPoke(0x41, 0x12, 0x00);   // SDP_CFG2 = ADC12→SDOUT1, ADC34→SDOUT2（标准 I2S）
```

顺带说明为什么之前"按键也听不见"：**按键和 VAD 走的是同一段 i2s_read**，
位宽错了两边一起废，跟触发方式无关。这一条上一版我解释成了"删掉 setFormat"，

## 13.2 I2S 改成显式双声道，软件抽左声道

`I2S_CHANNEL_FMT_ONLY_LEFT` 依赖驱动内部 mono 行为（有的版本会复制样本、
有的会跳采样），不确定。改成 `I2S_CHANNEL_FMT_RIGHT_LEFT` 后数据一定
是 `L R L R` 交织，再自己抽左声道，逻辑完全确定：

```cpp
static inline int takeLeft(const int16_t* src, int cnt, int16_t* dst) {
    int o = 0;
    for (int i = 0; i + 1 < cnt; i += 2) dst[o++] = src[i];
    return o;
}
```

ES7210 的 SDOUT1 上左=ADC1(MIC1)、右=ADC2；我们只开了 ADC1，取左即可。
播放侧不受影响（`playPcm()` 本来就是按 L/R 成对写的）。

**副作用**：一帧样本数减半（16ms/帧，原来当单声道读是 32ms），
所以 `VAD_ON_FRAMES 3→6`、`VAD_OFF_FRAMES 22→44` 补偿，时间尺度不变。

# 15. 2026-10-03 改版 7（★ 麦克风真凶：ES7210 的 PGA 增益实际是 0dB）

## 15.1 线索回顾：麦克风其实是通的，只是小了 40dB

改版 6 的日志里出现了两个决定性的现象：

```

[VAD] peak=25 raw=51 ...      raw 从 5 直接跳到 51 —— 麦克风"听见"喇叭了

[VAD] 说完了 32128 bytes (1.0s) 本段raw峰值=35 首8样本=-1 -2 0 1 1 0 0 0
```

判读：

1. **录音样本是"干净的小信号"**（±5 以内、无直流大偏移、不是随机大数）
   → 位宽/字节序/声道都是对的，否则读出来会是几十万的乱码或恒定值。
2. **声音进来时 raw 能到 35~51**，而安静时是 5
   → 麦克风通路是通的，动态也在，只是整体电平低了两个数量级。
3. **ASR 能听对"你好"**
   → 送上去的数据是可辨语音，不是噪声。

结论：**不是数字格式问题，是模拟增益问题。**

## 15.2 ★ 真凶：`init()` 写 0x10，注释说"16dB"，实际是 0dB

ES7210 数据手册 **REGISTER 0x43（MIC1 GAIN）** 原文：

| 位 | 名称 | 含义 |
|---|---|---|
| bit[7:5] | — | 保留 |
| **bit[4]** | **SELMIC1** | **1 = 选中 MIC1P/MIC1N 作为输入** |
| **bit[3:0]** | **MIC1GAIN** | 0=0dB, 1=3dB, 2=6dB … 11=33dB, **13=36dB**, 14=37.5dB |

Espressif 官方 `esp-bsp/components/es7210/es7210.c` 的写法是：

```c
/* Set MIC1-4 gain to 30dB */
ES7210_WRITE_REG(ES7210_MIC1_GAIN_REG43, mic_gain | 0x10);   // ← 那个 0x10 是 SELMIC 位
```

而 `lib/ES7210/src/ES7210.cpp` 的 `init()` 里写的是：

```cpp
writeReg(ES7210_MIC1_GAIN, 0x10);  // 16dB      ← ★ 注释把 bit4 当成增益位了
```

**0x10 拆开 = bit4(SELMIC1)=1 + bit[3:0]=0 → 真实增益 0dB。** 库作者以为
`0x10` 是"16dB"，其实它只完成了"选中 MIC1"，放大一档都没给。麦克风输出本来
就只有几十 mV 量级，再不给前置放大，进 ADC 就是小数点后几位的东西。

所以从第一版起，麦克风**从来没有被放大过**。这解释了全部现象：
`peak=1 / raw=5`、ASR 只能瞎猜、按键和 VAD 两条路一起哑。

## 15.3 修法：init() 之后直接补增益

```cpp

i2cPoke(0x41, 0x11, 0x60);                  // 字长 16bit + I2S（见 §13.1）
i2cPoke(0x41, 0x12, 0x00);                  // 非 TDM，ADC12→SDOUT1
i2cPoke(0x41, 0x43, 0x10 | MIC_PGA_CODE);   // ★ MIC1：SELMIC1 + 36dB
i2cPoke(0x41, 0x45, 0x10 | MIC_PGA_CODE);   //   MIC3：同上
```

`MIC_PGA_CODE` 放在 `ai_config.h`，默认 **13 = 36dB**（离满量程 37.5 只差一档）。
近场喊话削顶就往下调：`11`=33dB、`10`=30dB。

## 16.2 顺手修掉的两个"假警报"

同一份日志里 `ana=42(C3)` 和 `ADC1=FF(02)` 看着像配置坏了，其实芯片好好的 ——
`rawL=2161` 已经证明模拟通路完全正常。原因是 `i2cPeek()` 用的是
`endTransmission(false)`（重复起始）+ `delay(1)`，在这块板子上会**间歇性 NACK**。

> 教训：**自检读数不可信，比没有自检更糟** —— 会把人带到错误的方向上。

改法两条：

1. `i2cPeek()` 改成和 `lib/ES7210` 的 `readReg()` 一致：`STOP + delay(2)`，
   并且**最多重试 3 次**，三次都读不到才认 `0xFF`；`i2cPoke()` 补上 `delay(3)`（库的写法）。
2. **0x40（模拟供电）/ 0x60（ADC 使能）不再当判据** —— 回读不稳，只当参考值列出。
   报警只保留三个可信的：`0x11` 字长、`0x41` MICBIAS、`0x43` 增益。
   最终判据永远是 `[VAD] listening` 的 `rawL`。

# 18. 改版 10（2026-10-04）：VAD 判定重做 + ASR 前处理（治"叫不应 / 乱触发 / 识别不准"）

## 18.1 老陈反馈的三个症状

| 症状 | 说明 |
|---|---|
| 识别错字/不准 | 说对了也认不对 |
| 经常不触发 | 对着它说话半天没反应（叫不应） |
| 容易误触发 | 没人说话它自己开始录、乱识别 |

## 18.2 定位：三个症状是一根藤上的瓜

"叫不应"和"乱触发"看着矛盾，其实同一个根 —— **单帧硬判 + 连续计数**：

- **连续计数**：说话时字与字之间有瞬时低谷，只要一帧 RMS 掉到门限下，计数就清零
  → 6 帧永远攒不够 → **叫不应**；
- **单帧判门**：偶发噪声（关门/咳嗽/放杯子）冒头 96ms 就直接触发 → **乱触发**；
- **识别不准**：远场小声 + 空调/桌面低频轰鸣，送进 ASR 的信噪比不够。

## 18.3 改法

### (1) 触发：8 帧窗口投票（不再要求"连续"）
`AudioIO` 加 `_speechMask`（8bit 移位寄存器），每帧把 `rms > thr` 移进最低位，
`popcount(mask) ≥ VAD_ON_FRAMES(6)` 即判定开口。
人声起伏能攒够票（**更灵敏**），偶发噪声凑不满 8 帧里的 6 票（**更抗误触**）。
诊断日志新增 `投票=x/6`。

### (2) 收尾：3 帧 RMS 滑动平均（`VAD_SMOOTH_N`）
录音中用平滑后的 RMS 与 `0.6 × 阈值` 比较，防止话音里字间低谷把句子**提前切断**。
（原来用原始单帧 rms，抖动一大就误判"说完了"。）

### (3) TTS 后冷却延长（`VAD_COOLDOWN_MS` 600 → 1000ms）
TTS 播完后喇叭余音 + 房间混响没散尽就开听，会把自己刚放的话又当人声 → **自激误触发**。

### (4) ASR 前处理（`AudioIO::prepareAsr()`，开关 `ASR_PREPROCESS`）
`ai_print.cpp` 的 `turnTaken()` 里、`cloud.asr()` 之前调用：

- **80Hz 一阶高通**（`ASR_HPF_FC`）：切掉空调/风扇/桌面震动的低频轰鸣。
  人声主要在 300~3400Hz，切 80Hz 以下对语音无损，却能把噪声底压下来；
- **去直流 + 峰值归一化**到 -4.4dBFS（`ASR_TARGET_PEAK`），上限 +18dB（`ASR_MAX_GAIN`）。
  百度对"输入端电平偏小"的录音识别率明显下降，抬起来更稳；
- **峰值 < 200 视为静音，不放大** —— 免得把底噪一起抬起来；
- 日志：`[ASR] 预处理: 高通80Hz + 归一化 peak=xxxx gain=x.xx x`。

| `[VAD] … 投票=5/6`（差一票） | 门限偏高 / 增益不够 | `VAD_MULT` 2.5→2.2，或 `VAD_MIN_RMS` 150→130 |

# 22. 噪点根治 + 预览黏住 + 唤醒词 + 眼睛重画（2026-10-04 晚，改版13）

老陈上板反馈四件事，全部处理：

## 22.1 打印图片全是噪点 → 三道前处理 + 阈值模式（★本版最大改动）

**根因**（用老陈那张猫图实测确认）：模型给的插画带大量浅灰中间调，缩到 384 点后
被 Floyd–Steinberg 抖动**扩散成满屏斜纹噪点**（黑点占比 22%，几乎全是背景噪点）。
线稿图根本不需要抖动 —— 抖动是给照片模拟灰阶用的。

**改法**（打印前按顺序三道，全在 `text_bmp.cpp`，参数在 `ai_config.h`）：
1. **对比度拉伸** `IMG_CONTRAST`：解码后按 1%/99% 分位把灰度范围铺开（→8~247），
   浅灰线变实线、灰底变白底。预览和打印用同一份缓存，同时受益；
2. **去噪** `IMG_DENOISE`：打印前 3×3 均值模糊（权重 1-2-1/4/1-2-1），抹掉缩图残留的椒盐点；
3. **二值化模式** `IMG_BIN_MODE`：
   - `0` = **阈值二值化**（★默认，线稿首选）—— 按门限 `IMG_THRESHOLD`(默认145) 干净切分，无误差扩散 → 没有噪点；
   - `1` = Floyd–Steinberg 抖动（灰阶照片/素描才用）。

实测对比（`preview_compare.png`）：旧抖动版背景满屏噪点，新阈值版背景纯白、线条完整。
另修一个隐藏雷：`HTTPClient::setTimeout()` 参数是 uint16_t，原来 `IMG_TIMEOUT_MS 90000`
被静默截断成 24.5s（出图实测 20s，差点不够）→ 改 45000。
提示词同步加强："没有灰阶、没有阴影、没有渐变、没有纹理、没有网点"。

## 22.2 预览图"一闪而过" → 图片模式黏住

**根因**：`ttsPlay()` 第一块音频到达时回调里 `face.setState(FACE_SPEAK)`，
而 `setState()` 无条件 `_imageMode=false` —— 图刚画上去就被说话表情顶掉了。

**改法**：
- `Face::setState()` 在 `_imageMode` 下**只记录状态、不覆盖屏幕**；
  只有 `closeImage()`（打印完成 / 说"取消"）才真正切回动画；
- `drawAndPreview()` 开头先 `closeImage()` 收旧图；
- 新增**取消命令**："取消 / 算了 / 不打了 / 不要了 / 不打印 / 不画了 / 扔掉 / 删掉"

# 24. 唤醒词关闭（2026-10-04 夜，改版15）★ 结论性决定

## 24.1 实测证据：软件唤醒这条路不成立

老陈上板日志（关键三行）：

```
[VAD] 开始说话 rms=1512 thr=150 noise=60 (投票6/6)     ← 触发、录音都正常
[ASR] 预处理: 高通80Hz + 归一化 peak=5894 gain=3.34x   ← 前处理也正常
[ASR] "啊啊啊。"                                        ← ★ 元凶
[WAKE] 未唤醒，忽略: "啊啊啊。"
```

老陈喊的是"**阿蓝阿蓝**"，百度 ASR 输出的是"**啊啊啊。**" —— 连"阿蓝"两个字都没认出来。

**根因**：百度 ASR 是**给整句话设计的语言模型**。"阿蓝阿蓝"是个孤立叠词，不在它的
语言模型词表里；声学上"阿蓝"≈"阿兰/阿南/啊啊"，缺上下文时它按最可能的音去猜 →
"啊啊啊"。**这是识别源头的问题，不是匹配逻辑的问题**：

# 25. ★打印"显示完成但不出字"——共用 U8g2 缓冲的并发竞争（2026-10-04 夜，改版16）

## 25.1 老陈的现象

语音说"规划一个恐龙打印出来。" → 日志 `[UI] 打印中…` → `[UI] 打印完成`，
但纸上什么都没有。长按打测试页也有问题。

## 25.2 根因：两个核心在抢同一个 U8g2 缓冲，打印侧没加锁

`text_bmp.cpp` 里那个 `u8g2` 实例是 **打印和屏幕文字浮层共用的**（cnCanvas 命名空间
也用它）。而两边跑在不同核心：

| 谁 | 在哪 | 干什么 | 有没有锁 |
|---|---|---|---|
| 屏幕文字 | **core 0**，Face 动画任务，**每 90ms 一帧** | `Face::render() → screenText.overlayDialog() → drawTextLine() → cnCanvas::clear()+draw()` | ✅ 有 GfxGuard |
| 打印文字 | **core 1**，主循环 | `printText() → u8g2.clearBuffer()/drawUTF8()/getBufferPtr()` | ❌ **没有** |

于是时序上会这样：打印侧刚把字画进缓冲 → 屏幕侧下一帧 `clearBuffer()` 把它抹掉 →
`tileToPrintLines()` 拷到的是**全 0 的画布** → `printer.printImage()` 里
`countDots()==0` → `fireStrobe()` 直接 `return`（源码里就有一行 `if (dotCount == 0) return;`）
→ **纸照走，点一个不打** → 屏幕上却照样报"打印完成"。

**为什么以前没暴露**：老陈以前说"打印"时屏上都有生成的图 → 走的是
`printPhotoPending()`（那条路径**不用 u8g2**，所以没事）。**打印文字**是唯一走 U8g2
的打印路径，这次才第一次真正踩到。测试页也用 u8g2（下方的 MAC/IP 文字），同一个病。

**修法**（`text_bmp.cpp`）：
- `printText()`：字体设置 + `wrapLines`（要调 `getUTF8Width` 量宽）套一把 GfxGuard；
  每块**渲染**再套一把，**`printer.printImage()` 放锁外** —— 否则动画会卡住整个打印过程；
- `printTestPage()`：整段套 GfxGuard（测试页只几秒）；
- 新增 `[PRINT] … 墨点=N` 诊断日志：**N=0 就证明画布是空的**，一眼定位。

## 25.3 顺手修：打印命令把"要画的东西"截胡了

"规划一个恐龙**打印**出来。" 这句里有"打印"，被打印命令分支抢先命中，
结果只是把**上一条回复**打了一遍 —— 而老陈要的是"画个恐龙"。

新增 `isPurePrintCmd()`：把"打印"分两种——
- **纯打印指令**（"打印"/"打出来"/"帮我打印一下"）：去掉打印类词后不剩什么 → 打上一条回复；
- **夹带内容**（"…一个恐龙打印出来"）：去掉后还有实质内容 → **放给 AI 理解**（它会走画图工具）。

## 25.4 测试页加了"硬自检条"（重要诊断工具）

测试页最顶部现在是 **24 行点阵、完全不经 U8g2 的纯字节图案**：
`全黑8行 + 棋盘格8行 + 全黑8行`。用途：

| 现象 | 结论 |

```

[TP] 开始 w=384 h=240 tempADC=2869 heatMax=10 heatMin=5 steps=4 cool=0
```

三条结论：
1. `tempADC=2869` > 库的基准 `nomADC=280` → 走"偏冷"分支 → 加热时间取到

2. **21.8ms/行**、292 行**全部发完**、`[UI] 打印完成` 出现 → **软件链路完整**；

→ **电池保护板过流保护（一旦触发就锁死，后面全没电）**，而不是软件问题。

## 27.4 关于小智（xiaozhi-esp32）——老陈问的两件事

### Q1：能不能用他们的软件、但不走他们的服务器？

| 你的诉求 | 现实 |
|---|---|
| 只要软件、不要服务器 | 拿到的是**没有大脑的空壳**（能听能放，但不会思考） |
| 接入"他们的大模型" | 官方服务器默认跑 **Qwen 实时模型**；不走它，就接不到 |

`xinnan-tech/xiaozhi-esp32-server`（Python）、`joey-zhou/xiaozhi-esp32-server-java`、
`AnimeAIChat/xiaozhi-server-go`、`hackers365/xiaozhi-esp32-server-golang`。
在服务端里 ASR/LLM/TTS 想接谁接谁（DeepSeek、通义、百度都行）。
设备的服务器地址通过 `Kconfig` 的 **`OTA_URL`**（默认 `https://api.tenclass.net/xiaozhi/ota/`）
指定 —— 改成你自己的地址即可。

### ★ 我的建议：**不要把阿蓝推倒重来**

**阿蓝现在这条路（自己写固件 + 直连百度 ASR/TTS + DeepSeek）本质上已经是
"不要他们服务器"的终极形态了**；换成小智 = 固件换掉 + **额外再养一台服务器**（PC 常开或云）。
而且小智**没有热敏打印的板级支持**，打印这块要全部自己重写。

**真正值得从它身上抄的，只有一件事：全链路流式 + WebSocket 长连接**（它的响应快主要靠这个）。
这个我们**不需要额外服务器**也能做（直接连百度/DeepSeek 的流式接口 + HTTP keep-alive），
已在 §23 的提速里做了一半（TTS 缓存 + 流式播放），还能继续做 ASR 流式上传、LLM 真流式。

**结论：继续把阿蓝做顺。小智当参考，不当替代。**
